# 원고 작성 원칙과 문장 지침

원고 형식(고정 섹션·frontmatter·검증 규칙)은 `scripts/README.md` 가 규범이다.
이 문서는 그 형식 안에 "무엇을 어떻게 쓰는가"를 다룬다.

## 대원칙

1. **화면의 문구를 그대로 인용한다.** 버튼이 "신청 승인"이면 원고도 "신청 승인"이다.
   "승인 버튼" 으로 의역하지 않는다. 독자는 원고와 화면을 대조하며 따라온다.
   에러 메시지·플레이스홀더·확인 문구도 코드에서 복사해 따옴표로 인용한다.
2. **렌더로 확인한 것만 배치를 서술한다.** 캡처에 없는 화면의 버튼 위치·순서를
   코드만 보고 쓰지 않는다. 렌더 못 한 화면은 "무엇을 할 수 있다"까지만 쓴다.
3. **독자는 이 화면을 처음 본다.** 개발자에게 자명한 것(저장하면 저장된다)이 아니라
   불안한 것(저장 전에 나가면 어떻게 되나)을 쓴다.

## 섹션별 지침

- **이 기능은?** — 한두 문장. "무엇을 하러 올 때 쓰는가"로 시작한다.
- **⚠️ 주의** — 되돌릴 수 없는 동작, 과금, 전체 공개 등. 코드에서 근거를 확인한
  것만 쓴다 (삭제 API 에 soft-delete 가 있으면 "되돌릴 수 없다"고 쓰면 안 된다).
- **어디에 있나요?** — 메뉴 경로를 `>` 로: "좌측 메뉴 > **회원 관리**".
- **화면 구성** — 캡처 뱃지와 번호·순서 1:1. 각 항목은 "**이름** — 역할" 한 줄.
  뱃지 없는 요소는 목록에 넣지 않는다 (build 가 개수 불일치로 실패한다).
- **방법** — 1단계 1동작. "○○를 누릅니다" 처럼 동사로 끝낸다.
  입력 규칙(최소 길이, 형식)은 검증 코드에서 읽어 해당 단계에 붙인다.
- **그러면?** — 성공 시 화면 변화 + 부수 효과(메일 발송 등, 코드 근거 필수).
- **안 될 때는?** — 실제 에러 분기에서 뽑는다. 에러 문구를 그대로 인용하고
  "→ 어떻게 하라"를 붙인다. 코드에 없는 에러를 상상해서 쓰지 않는다.

## 문장

- 경어체 "~합니다/~하세요". 독자 호칭은 MANUAL.md 를 따른다.
- 개발 용어 금지: 컴포넌트, API, 렌더링, 토큰, 세션 → 화면, 정보, 표시, 로그인 상태.
- 한 문장 하나의 내용. 40자를 넘기면 나눈다.
- UI 요소 이름만 **굵게**. 강조를 남발하면 강조가 사라진다.

## fixture 데이터 (캡처 명세의 routes mock)

- 그럴듯한 한글 값: 이름 김영희/이철수, 회사 (주)한빛상사, 이메일 `yh.kim@example.com`.
- **실존 인물·실제 연락처·실제 고객 데이터 금지.** 전화는 010-0000-0000,
  도메인은 example.com 계열만. (Phase 4 에서 패턴 스캔으로 걸러진다)
- 날짜는 `freezeTime` 근처로 자연스럽게 (가입일이 미래면 안 된다).
- 목록은 2~4행이면 충분하다. 상태 컬럼이 있으면 서로 다른 상태를 섞는다.

## 〔확인:〕 마커

사용자만 아는 값은 자리에 마커를 박고 진행한다:

```markdown
문의: 〔확인: 고객센터 연락처〕 로 연락하세요.
```

동시에 `docs/manual/_질문.md` 에 같은 항목명으로 기록:

```markdown
- [ ] 고객센터 연락처 — 03-approve.md 에서 사용. 코드에서 못 찾음
```

항목명이 양쪽에서 동일해야 Phase 4 의 grep 대조가 성립한다.
