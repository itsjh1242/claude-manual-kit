# Phase 1 상세 — 코드 조사 절차

## 1. 독자(역할) 도출

라우트 정의와 권한 가드에서 역할을 읽는다. 찾는 곳:

- 라우터 설정: 경로 그룹(`/admin/*`, `/app/*`), 가드 컴포넌트(`RequireAuth`, `AdminRoute`),
  미들웨어(Next.js `middleware.ts`), 레이아웃 분기
- 인증 코드: 토큰 payload 의 role 필드, `user.role === 'admin'` 류의 분기
- 메뉴/네비게이션: 역할별로 다른 메뉴를 그리는 조건문

역할 하나 = 문서 하나. 역할 구분이 없으면 문서는 하나("사용자용")다.
호칭은 MANUAL.md 의 독자 호칭을 따르고, 없으면 코드의 역할명을 한국어로 옮겨
`_질문.md` 에 확인 요청을 남긴다.

## 2. 기능 목록 만들기

"사용자가 할 수 있는 일 하나 = 항목 하나". 판별 기준:

- ✅ "회원 가입 신청을 승인하기" — 동사가 있는 과업
- ❌ "회원 관리 페이지" — 화면 이름. 화면 하나에 과업이 여럿이면 항목도 여럿이다
- 조회만 하는 화면도 과업이다: "정산 내역 확인하기"

순서는 사용자 여정 순: 계정/로그인 → 처음 한 번 하는 설정 → 일상 업무(빈도순)
→ 가끔 하는 관리 → 예외/복구. 화면 트리 순서가 아니다.

각 항목에 적어둘 것: 진입 경로(URL), 관련 컴포넌트 파일, 필요한 권한,
호출하는 API(3에서 채움).

## 3. API 표면 추출

각 화면이 부르는 엔드포인트와 응답 형태를 캡처 fixture 의 근거로 확보한다.

1. **TypeScript 타입 정의가 1순위 근거.** API 응답 타입, zod 스키마,
   OpenAPI 생성물이 있으면 그대로 mock 의 형태로 쓴다.
2. 없으면 렌더 코드에서 역추적: 컴포넌트가 `data.items.map(...)` 하고
   `item.name`, `item.status` 를 읽으면 그것이 응답 스키마다.
3. 화면당 기록: `GET /api/members?page=` → `{ items: Member[], total: number }` 식으로.
4. 공통 호출(내 정보, 알림 개수, 설정 등)은 한 번 정리해 모든 명세에 재사용한다.
   capture.mjs 의 "매칭 안 된 API 호출" 경고가 누락을 알려주니 완벽할 필요는 없다.

## 4. 규모 상한

독자당 기능이 20개를 넘으면:

- 핵심 여정(로그인부터 가장 빈번한 과업까지)으로 1차 범위를 자른다
- 나머지는 `_목차.md` 의 "2차 범위" 절에 사유와 함께 기록한다
- 사용자에게 묻지 않는다 — 1차 범위로 진행하고 최종 보고에서 알린다

## 5. _목차.md 형식

```markdown
# <독자> 설명서 목차

- 근거: 라우트 <파일>, 가드 <파일>
- 순서 기준: <한 줄>

## 1차 범위
| # | 기능 | 진입 경로 | 컴포넌트 | API | 상태 |
|---|---|---|---|---|---|
| 1 | 로그인하기 | /login | LoginPage.tsx | POST /api/login | ✅ 완료 |
| 2 | 회원 목록 확인하기 | /admin/members | MemberList.tsx | GET /api/members | 🔨 캡처까지 |
| 3 | 가입 신청 승인하기 | 〃 | 〃 | POST /api/members/:id/approve | ⬜ |

## 2차 범위 (이번에 제외)
- 감사 로그 조회 — 사용 빈도 낮음, 1차 여정 밖

## 제외 (문서화 안 함)
- /debug — 개발자 전용 화면
```

상태 값: ⬜ 미착수 / 🔨 진행 중(어디까지인지 명기) / ✅ 완료.
기능 하나 끝날 때마다 갱신한다 — 이 파일이 재개의 근거다.
