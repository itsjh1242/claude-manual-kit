# 사용 설명서 생성

코드베이스 → 독자별 기능 목록 → 주석 달린 화면 캡처 → PDF 설명서.
실제 로그인 없이 네트워크 인터셉트로 화면을 재현하며, 프로젝트 코드는 건드리지 않는다.

도구는 이 SKILL.md 와 같은 디렉토리의 `scripts/` 에 있다 (사용법·스키마는 `scripts/README.md`):
- `scripts/capture.mjs` — 캡처 명세 JSON → 주석(뱃지·박스·확대) 입힌 PNG
- `scripts/build.mjs` — 원고(.md) + PNG → PDF (Typst 0.15.x 필요)
- `scripts/validate.mjs` — 개인정보 패턴 스캔 + 〔확인:〕 마커 대조 (Phase 4)

최초 실행 시 `scripts/` 에서 `npm install && npx playwright install chromium`,
그리고 typst 설치 여부를 확인한다 (`brew install typst`).

산출물은 대상 프로젝트의 `docs/manual/` 에 만든다:

```
docs/manual/
├─ _질문.md                # 사용자 확인 필요 항목 (〔확인:〕 마커와 1:1)
└─ <독자>/                 # 독자(역할) 하나 = 문서 하나
   ├─ _목차.md             # 기능 목록·순서 근거·제외 항목·진행 상태 — 재개의 근거
   ├─ specs/               # 캡처 명세 JSON
   ├─ captures/            # 캡처 PNG
   ├─ manuscript/          # doc.json + NN-*.md 원고
   └─ manual.pdf
```

## 질문 정책 (모든 Phase 공통)

루프 중에는 사용자에게 묻지 않는다. 스스로 판단하고 결과만 보고한다.

- 빌드·실행 명령, 파일 위치, 코드 구조 → 코드베이스를 읽고 판단
- 모르는 API나 라이브러리 → 웹검색으로 확인하고 진행
- 판단이 갈리면 변경 범위가 작은 쪽을 택하고 근거를 `_목차.md` 에 남긴다

사용자만 아는 것(문의처 실제 값, 비즈니스 문구, "1영업일 내 연락" 같은 클레임)은
멈추지 말고 본문에 `〔확인: 항목명〕` 마커를 박고 `docs/manual/_질문.md` 에 기록 후
계속 간다. 마커 형식은 반드시 `〔확인: ...〕` 로 통일한다 — Phase 4 에서 grep 으로 대조한다.

렌더가 안 되는 화면은 그 범위를 글로만 쓰고, 배치 서술은 생략한다.
**렌더로 확인하지 않은 화면 구성을 코드만 보고 서술하지 않는다.**
버튼 순서를 코드 순서로 짐작하면 틀린다.

## 프로젝트별 설정 — MANUAL.md

프로젝트 루트의 `MANUAL.md` 를 먼저 읽는다. 거기 답이 있으면 추정하지 않고 그대로 쓴다.
기록 대상: 서비스명, 문의처, readers(아래 「독자(문서) 결정」), 브랜드 색,
제외할 기능, 숨길 selector(쿠키 배너 등), fixture 작성 규칙,
개인정보 화이트리스트(`## validate-whitelist` 절 — 의도한 예시값을 등록).

없으면 최초 실행 시 위 항목들을 빈 칸/추정값으로 채운 템플릿을 생성하고,
추정한 값은 전부 `_질문.md` 에 남긴다.

## Phase 0 — 대상 파악 (자동, 묻지 않는다)

1. dev 서버 탐지: 실행 중인 포트를 먼저 확인 (`lsof -i -P | grep LISTEN` 등).
   없으면 package.json scripts 에서 추론해 백그라운드로 띄우고 응답할 때까지 대기.
   추론이 실패하거나 후보가 여럿일 때만 질문한다.
2. 파악할 것: 프레임워크, 라우터, 인증 방식(토큰이 저장되는 스토리지 키),
   API 클라이언트(base URL, 공통 헤더), dev 서버 base URL.
3. `MANUAL.md` 가 있으면 읽는다.
4. 확정 결과를 한 줄로 보고하고 바로 Phase 1 로 간다.
   예: "Vite+React, react-router, localStorage `accessToken`, `/api` 프록시, :5173 — 조사 시작"

## 독자(문서) 결정

독자 하나 = 문서 하나. **코드상 역할과 1:1이 아닐 수 있다.** 우선순위:

1. **사용자가 요청에서 지정한 경우** → 그대로 따른다.
   ("관리자 설명서만", "참가사용과 관리자용 두 개", "전체 하나로")
2. **MANUAL.md 에 readers 설정이 있으면** → 그대로 따른다.
3. 둘 다 없으면 **코드에서 도출한다** (기준은 `references/investigate.md`).
   도출 결과를 MANUAL.md 의 readers 에 기록하고, 추정임을 `_질문.md` 에 남긴다.

MANUAL.md 의 readers 형식 — 독자 하나당 블록 하나:

```markdown
## readers

### admin                          <!-- id: docs/manual/ 아래 폴더명 -->
- 문서 제목: ○○몰 관리자 설명서    <!-- 표지에 나갈 이름 -->
- 포함할 코드 역할: admin, manager  <!-- 여러 역할을 한 문서로 묶을 수 있다 -->
- 호칭: 관리자
- 제외할 기능: 감사 로그 조회       <!-- 있으면 -->
```

**전체 문서 모드**: "전체 기능", "역할 구분 없이" 같은 요청이면 `all` 이라는
단일 독자로 처리한다. 역할별 접근 제한이 있는 기능은 본문(이 기능은? 또는 주의)에
"이 기능은 관리자만 사용할 수 있습니다" 같은 표시를 넣는다.

**여러 독자를 만들 때**: 문서마다 기능 번호는 각각 1부터 시작한다.
상호 참조(`→ [기능id]`)도 문서 내부로 한정한다 — 다른 문서의 기능을 가리키지 않는다.
기능을 독자에 배정할 때는 접근 권한을 기준으로 한다. 고객용 문서에 관리자 화면이
섞이면 안 된다.

## Phase 1 — 조사

절차 상세는 `references/investigate.md` 를 읽고 따른다. 골자:

1. 위 「독자(문서) 결정」에 따라 독자를 확정한다. 코드에서 도출하는 경우의
   묶음 판단 기준은 investigate.md 에 있다.
2. 독자별 **기능 목록**: "사용자가 할 수 있는 일 하나 = 항목 하나". 화면 나열이 아니다.
   순서는 사용자 여정 순 (첫 로그인 → 일상 업무 → 예외 상황).
3. **API 표면 추출**: 각 화면이 부르는 엔드포인트와 응답 타입.
   TypeScript 타입 정의가 1순위 근거, 없으면 렌더 코드에서 역추적.
4. **규모 상한**: 독자당 기능이 20개를 넘으면 핵심 여정으로 1차 범위를 자르고
   나머지는 2차 범위로 `_목차.md` 에 기록한다.
5. 결과를 `docs/manual/<독자>/_목차.md` 에 기록 (형식은 investigate.md 참고).

## Phase 2 — 기능 단위 루프 (기능마다 반복)

원고 문장 지침은 `references/writing.md`, 막히면 `references/troubleshoot.md`.

a. **코드에서 실제 문구를 읽는다** — 버튼명, 검증 규칙, 에러 메시지.
   의역하지 않고 그대로 인용한다. 독자가 화면과 대조해야 하기 때문이다.
b. **fixture 작성** — 그 화면에 필요한 상태(빈 목록/채워진 목록/오류 등)를
   캡처 명세의 `routes` mock 으로 만든다. 데이터는 그럴듯한 한글 예시값으로.
   이 값이 그대로 PDF에 박힌다. 실존 인물·실제 연락처를 쓰지 않는다.
c. 캡처 명세 JSON 작성 → `node scripts/capture.mjs --spec ... --out ... --base-url ... --quiet`
   명세 id 는 `<독자>-<기능번호 2자리>-<상태>` 로 짓는다 (예: `admin-03-empty`,
   `admin-03-filled`). 루프에서는 항상 `--quiet` — 판정 줄과 경고만 남아 컨텍스트를 아낀다.
   화면이 세로로 길면 `clip` 으로 설명에 필요한 영역만 찍는다 — 긴 이미지는
   PDF 에서 페이지에 맞춰 축소돼 글자가 작아진다.
d. **생성된 PNG를 Read 로 실제로 열어본다.** 확인할 것:
   - 뱃지가 의도한 요소를 가리키는가
   - 화면이 제대로 렌더됐는가 (로딩 스피너/스켈레톤 상태로 멈춰 있지 않은가)
   - `route 와 매칭되지 않은 API 호출` 경고가 있으면 fixture 에 추가하고 재촬영
e. **원고 작성** — `scripts/README.md` 의 고정 마크다운 형식으로.
   "화면 구성" 번호는 캡처 뱃지와 1:1 (build 가 번호 합집합을 검사한다).
   다른 기능 언급은 `→ [기능id]` 로 쓴다 (id = 파일명 `NN-<id>.md` 의 `<id>`).
f. `_목차.md` 의 진행 상태를 갱신한다 (기능 하나 끝날 때마다).

## Phase 3 — 조립

전 기능 완료 후 실행한다. 상호 참조는 id 기반(`→ [기능id]`)이라 build 가 번호와
쪽수를 계산한다 — **기능 순서를 바꿔도 원고를 고칠 필요가 없다.** 순서 변경은
파일명의 번호만 바꾸면 되고, 번호·목차·참조 쪽수는 build 가 알아서 맞춘다.

```
node scripts/build.mjs --manuscript <manuscript/> --captures <captures/> \
  --specs <specs/> --out <독자>/manual.pdf
```

`BUILD: FAIL` 이면 사유(뱃지 번호 불일치, 캡처 누락, 깨진 참조)를 고치고 재실행.

**성공해도 끝이 아니다 — PDF 전체를 Read 로 넘겨 보며 조판을 직접 확인하고,
발견한 문제는 보고가 아니라 수정으로 끝낸다.** "clip 을 권장합니다"라고
사용자에게 말하고 멈추지 않는다 — 스스로 고치고 결과를 보고한다:

- "세로로 길어 축소" 경고가 나온 캡처: PDF 에서 글자를 실제로 보고, 배율이
  60% 미만이면 고친다. 뱃지 대상들이 한 영역에 모여 있으면 명세에 `clip` 추가,
  페이지 전체에 흩어져 있으면(clip 을 넣어도 주석 합집합 때문에 안 줄어든다)
  캡처를 상/하 두 장으로 나누고 "화면 구성"도 묶음 두 개로 재구성한다.
  → 재촬영 → 재빌드 → 다시 확인까지가 한 사이클이다.
- 페이지가 반 이상 비어 있으면: 큰 이미지가 다음 페이지로 밀린 것. 위와 같이 수정.
- 표지·목차 쪽수·상호 참조 쪽수·뱃지 색이 정상인지 훑는다.

조판 문제는 원고를 고치는 게 아니라 캡처(clip·분할)에서 고치는 것이 원칙이다.

## Phase 4 — 검증과 보고

1. **최종 검증 스크립트**를 독자마다 실행한다:
   ```
   node scripts/validate.mjs --manuscript <manuscript/> --specs <specs/> \
     --captures <captures/> --questions docs/manual/_질문.md --manual-md MANUAL.md
   ```
   - 개인정보 패턴(이메일·휴대폰·전화·카드·주민번호)을 원고·fixture·캡처 파일명에서
     스캔한다. 실제 값이면 fixture 를 고치고 재촬영, 의도한 예시값이면 MANUAL.md 의
     `## validate-whitelist` 에 추가하고 재실행.
   - `〔확인:〕` 마커 ↔ `_질문.md` 항목 1:1 대조. 한쪽에만 있으면 맞춘다.
   `VALIDATE: OK` 가 나올 때까지 반복한다.
2. **최종 보고**: PDF 경로, 독자·기능 수, `_질문.md` 요약(사용자가 답해야 할 것).
3. **커밋하지 않는다.** 사용자가 검토 후 직접 한다.

## 재개

중간에 끊기면 `docs/manual/<독자>/_목차.md` 의 진행 상태를 읽고
다음 미완료 기능부터 이어간다. 처음부터 다시 돌지 않는다.
완료 표시된 기능의 캡처·원고는 다시 만들지 않는다.
